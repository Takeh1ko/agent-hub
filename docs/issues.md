# Замечания к ahub (с сервера)

Что хаб по умолчанию делает плохо или не делает — записывает оркестратор (Claude) по ходу работы, исправляет
владелец. Новое — сверху. Формат: дата · что видно · почему плохо · как исправить (предложение) · статус.

## 2026-10-06 · Нет разрешений на уровне задачи — работники отказываются от живых проверок
- **Видно:** разведки T3/T4 (PlayerUP) не стали читать боевую БД, env и проверять прокси: «per worktree-only rule»,
  «sandbox rule forbids real data/secrets». Главные вопросы владельца остались без ответа, оркестратор доделал сам.
- **Почему:** у задачи нет поля «что разрешено». Разрешения можно только вписать прозой в спецификацию, а общие правила
  проекта (`rules`) их перебивают — модель выбирает осторожный вариант.
- **Предложение:** поле задачи `--allow "prod-db:read,live:playerok,logs,tokens:read"` (и в `draft`), которое хаб
  вставляет в промпт отдельным блоком «Разрешения владельца — важнее правил проекта», а ревьюеры не штрафуют за их
  использование. Отчёт разведки «не проверил, потому что нельзя» при выданном разрешении — повод для rework.
- **Статус:** обход — раздел «Разрешения владельца» в спецификации + пункт в `docs/agents/rules.md` PlayerUP.

## 2026-10-06 · DONE приходит с задержкой до 2 мин, а `ahub status T<id>` молча гасит событие
- **Видно:** T2 закончилась, владелец заметил это раньше оркестратора; оркестратор вызвал `ahub status T2` — событие
  подтвердилось и уже не пришло в `watch`. Со стороны выглядит как «хаб не дёрнул».
- **Почему:** `GROUP_WINDOW_MS = 120_000` (`events.py`) для всех не-срочных событий, включая `done`/`needs_decision`.
- **Предложение:** `done`/`needs_decision`/`error` — окно 10–15 с (или срочные при пустой очереди); в `ahub status`
  писать «событие подтверждено» явно.
- **Ещё:** `error` (упал хук `task_setup` у T5/T6) тоже ждёт окно 2 мин — авария стоит, а оркестратор не знает.
  Хук подготовки задачи стоит проверять заранее (`ahub doctor` / `ahub setup`: пробный прогон `task_setup`/`task_cleanup`).
- **Статус:** открыто.

## 2026-10-06 · `task new` в неподключённый проект ставит задачу в очередь молча
- **Видно:** `ahub task new` в каталоге с `.hub.toml`, но без `ahub setup` → «T2 queued», задача висит; только
  `ahub projects` показывает «! project has tasks but is not connected to the hub».
- **Предложение:** отказ с подсказкой `ahub setup <path>` (или подключать автоматически).
- **Статус:** открыто.

## 2026-10-06 · `.hub.toml` в git с путями машины владельца
- **Видно:** в репо хаба и PlayerUP `worktrees`/`python`/`root`/хуки — `$HOME/Projects/Python/...`,
  `/home/takehiko/...`. На сервере правятся руками и висят незакоммиченными (`M .hub.toml`).
- **Предложение:** пути относительно корня проекта, либо локальный `.hub.local.toml` (в `.gitignore`) поверх общего.
- **Статус:** открыто.

## 2026-10-06 · `ahub setup` пишет «Service —», хотя `ahub.service` работает
- **Видно:** `ahub setup /root/Project/ahub-v3 --yes` → «Service —» при активном `systemctl --user ahub`.
- **Предложение:** показывать фактическое состояние юнита.
- **Статус:** открыто, мелочь.

## 2026-10-06 · Ложная ТРЕВОГА «codex fails to list models» без установленного codex
- **Видно:** наблюдатель тревожил каждые ~10 мин; codex на сервере не ставился.
- **Почему:** `catalog()`/`login()` писали WARNING при отсутствии бинарника, `_log_suspicions` берёт любые WARNING.
- **Статус:** исправлено T2 в ветке `server-fixes` (3cac1ff), стоит на сервере из pipx; в GitHub не отправлено.
  Остаётся: `_log_suspicions` по-прежнему не фильтрует выключенные/неиспользуемые провайдеры.
